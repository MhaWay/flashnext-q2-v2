The operational default from this matrix is **k=1**. It wins six of eight
cells and gives the best workload-balanced result. k=2 is worth retaining as
an experimental single-stream code mode, where it is 2.7% above k=1, but three
repeats do not establish that small difference robustly. k=3 never wins a
cell. At eight concurrent prose streams, speculative decode is already
counterproductive and k=0 is 7.2% faster than k=1.

The short decode metric is usable despite the later-discovered SSE boundary
bug. Across all 96 measured rows,
`decode_window / (wall_time - TTFT)` has mean `1.00037` and range
`0.99997–1.00086`. There were no invisible trailing tokens in these requests,
so changing the boundary to response completion does not materially alter the
short-matrix conclusion.

## Acceptance and effective cost

At k=3, acceptance differs materially by workload. The values below aggregate
the four stream counts. `P2|P1` and `P3|P2` are conditional acceptance rates:

| Workload | P1 | P2 given P1 | P3 given P2 |
|:---|---:|---:|---:|
| prose | about 65% | about 60% | about 58% |
| code | about 78% | about 77% | about 79% |

The draft does not collapse with depth on code. k=3 loses because the marginal
accepted tokens cost too much, not because the third proposal is intrinsically
bad.

Using `Y_k = 1 + accepted_tokens / draft_cycles` and normalizing each matched
cell to its k=0 cycle cost gives the following approximate additional cost per
draft depth:

| Streams | First step | Second step | Third step |
|---:|---:|---:|---:|
| 1 | 0.50x k=0 cycle | 0.37x | 0.39x |
| 2 | 0.49x | 0.49x | 0.44x |
| 4 | 0.65x | 0.63x | 0.60x |
| 8 | 0.78x | 0.75x | 0.74x |

This is a combined target-shape, draft-forward, QSA metadata, scheduler and
graph cost. It is not a pure draft-model timing. Its strong dependence on
stream count shows that a single constant `d` cannot describe this runtime.

At one stream, the best observed throughput is 17.28 tok/s for code and 15.43
tok/s for prose. Reaching 70 tok/s therefore still requires roughly 4.1–4.5x
end-to-end improvement. MTP contributes useful double-digit gains at low
concurrency, but it cannot close the kernel/runtime gap by itself.

## Long-context run is not a valid result

The long phase contains six completed rows and one failed row, all at k=0. It
did not reach k=1 or 250K.

| Nominal context | Actual prompt tokens | Warm/cold state | TTFT | Reported decode |
|---:|---:|:---|---:|---:|
| 64 | 132 warmup / 135 measured | uncached | 0.544 / 0.319 s | 13.47 / 14.11 tok/s |
| 4,096 | 471 / 469 | uncached | 0.572 / 0.554 s | 14.06 / 14.03 tok/s |
| 32,768 | 3,435 warmup | cold | 3.199 s | 14.03 tok/s |
| 32,768 | 3,438 measured | 3,200 cached tokens | 0.445 s | **591.95 tok/s, invalid** |
| 131,072 | unavailable | timed out | unavailable | unavailable |

Three independent measurement faults invalidate this phase:

1. The prompt generator produced about one tenth of the requested long context.
   The `32768` case contained only 3,438 model tokens.
2. The unique nonce was appended after the document. Prefix caching therefore
   reused 3,200 of 3,438 tokens in the measured `32768` request, or 93.1%.
3. Decode timing ended at the last visible text delta. The concise-answer
   prompt emitted EOS early, while `ignore_eos=true` continued accounting
   tokens. The request took 36.919 s, but only 0.863 s was counted as decode,
   creating the impossible 591.95 tok/s result. Using response completion gives
   about 14.01 tok/s, consistent with the cold run.

The 131,072 warmup timed out after 5,400 seconds. Its metrics show one PLE
lookup, no prompt/generation tokens and a host `MemAvailable` minimum of
27.892 GiB, versus about 49–50 GiB in completed long rows. The archive also
contains a later config-only 131,072 measured attempt. That means the old
harness continued after the failed warmup and may have queued behind a request
that the server had not cancelled. No conclusion about 131K or 250K TTFT can
be drawn from this bundle.

## Profiler status

`profile_check.json` does not prove that NCU is unavailable. The host has no
`ncu`, but the container probe invoked `bash -lc` after an image whose
entrypoint is `vllm`. The returned error is therefore from the vLLM CLI:
`unrecognized arguments: -lc ...`. The corrected probe overrides the image
entrypoint with `--entrypoint bash`; it must be rerun on the GB10.

## Changes made after this review

The Phase 0 harness now:

- prefixes each request with its nonce, invalidating the whole cacheable prompt;
- calibrates long prompts against the live model's `/tokenize` endpoint and
  records target count, calibrated count, bytes and hash;
- measures decode through completion of the SSE response, including generated
  tokens that do not produce visible text;
- records a content hash of the measurement harness as well as the frozen
  baseline hash;
- aborts the sweep on a failed cell instead of starting the next request on a
  potentially unhealthy server;
- overrides the container entrypoint for the real NCU probe;
- tests the invisible-token case in the mock server.

## Decision

Use k=1 as the current general decode setting and k=0 for throughput-oriented
high-concurrency prose. Do not promote k=2 or k=3 globally. Start the kernel
profiling/rewrite track now, because the short matrix already isolates a
roughly fourfold single-stream gap that MTP tuning cannot remove.

Rerun only the corrected profiler check and long-context phase before making
any TTFT, 131K or 250K claim. The completed short matrix does not need an
immediate rerun for the k decision.

## Corrected 32K follow-up

The corrected 32K prompt contained 32,741 actual tokens. With an 8192-token
scheduler chunk, k=0 produced no first token in 900 seconds. vLLM recorded no
prompt or generation progress after one completed 21.46 ms PLE lookup, while
host `MemAvailable` fell from 50.69 to 32.93 GiB. This isolates the failure
after PLE and is consistent with a first-use JIT/Inductor pathology in the
real M=8192 compiled region. It is not evidence of PLE or SSD latency.

Repeating the same context with `MTP_BATCHED_TOKENS=4096` completed normally:

| Mode | Actual prompt | TTFT | Approx. prefill | Decode |
|:---|---:|---:|---:|---:|
| k=0 | 32,741 | 27.703 s | 1,182 tok/s | 13.755 tok/s |
| k=1 | 32,740 | 29.076 s | 1,126 tok/s | 15.035 tok/s |

The k=1 cell accepted 12 tokens across 19 draft cycles. Its decode throughput
was 9.3% above k=0, but the single observed TTFT was 1.37 s longer. For this
32-token completion k=0 therefore finished first. Extrapolating these two
single runs gives a rough break-even near 220 generated tokens; this is a
diagnostic estimate, not a promoted policy, until repeated.

The previous summary output mixed this rerun with legacy long rows because a
standalone `sweep-long` reused the short session ID. The harness now assigns a
new long-run session, records its parent short session and defaults to the
validated 4096-token chunk, preventing cross-configuration aggregation.
